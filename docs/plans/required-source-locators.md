# Required source locators and analysis cache identities

Implementation plan for finding 1, based on `8c95b4a`. No API migration or frontend change is intended.

## Outcome

Every discovered session has an exact, typed instruction for loading it. Display paths and HTTP input are never used to construct that instruction. File analysis and OpenCode analysis continue to use different freshness checks, but the cache no longer describes an OpenCode snapshot as a zero-byte Pi file. Clients can continue to use conditional requests; the literal analysis ETags may change once on upgrade.

## 1. Make the catalogue locator mandatory

- Start in `src/server/mod.rs` (`SessionFile`, `source_locator`), `src/server/catalog.rs` (Pi discovery) and `src/server/sources.rs` (the other five readers). Change `Option<SessionLocator>` to `SessionLocator` and remove the path fallback. For Pi use the actual canonical `PathBuf` already in the discovery loop, not the lossy UTF-8 string used for display. Keep source references and their hash inputs unchanged. Use native paths for Pi path deduplication across roots as well.
- Update every catalogue entry constructor and test fixture. In the source-specific deduplication loops, keep the existing path vs native-ID rules; making the locator non-optional does not by itself prove the enum variant matches the reader. Do not silently discard a session on a variant mismatch.
- Borrow the stored locator for synchronous consumers. Clone it where ownership is required by a blocking task, totals cache or async service. Check the analysis and item-content routes in `src/server/routes.rs`, `src/server/totals.rs`, and CLI report/show/turns consumers. Do not add a default locator to make fixture construction easier.
- Make the locator authoritative for `harness`. Use an exhaustive `SessionLocator::harness()` mapping; have entry construction set the serialised harness from the locator rather than accepting an independent harness argument. Replace the `..fixture_session("", "")` pattern in the multi-harness startup-summary tests with matching locators. Test the mapping for every reader.
- Retain the current `SessionFile` JSON shape and `#[serde(skip)]` on its internal fields. Keep internal entry equality, catalogue change detection and `TotalKey::of` unchanged. Splitting public and internal structs or moving discovery outside `server` is optional follow-up work, not a prerequisite for correctly loading a session.
- Check: the six source fixtures list the same IDs, visible paths, omission of optional fields, ordering and relationships as before. Assert the route never serialises locator, database path, internal revision or nanosecond fingerprint. Under `#[cfg(target_os = "linux")]`, cover a Pi file under a non-UTF-8 parent directory: the catalogue must retain the real path and load the fixture using it. Keep the display string policy unchanged.

## 2. Carry a file locator through analysis, including the injected executor

- In `src/source.rs`, represent `SessionLocator` as either `File(FileLocator)` or the existing OpenCode database path plus native session ID. `FileLocator` contains `path: PathBuf` and a closed reader kind (Pi, Claude Code with `FileKind`, VS Code Copilot, Codex, or Copilot). Move the reader discriminator out of `server/analysis.rs`; define it once, with the loading code. Update exhaustive matches in loading, totals, discovery and source fixtures together. No trait registry or serialisation for locators.
- Let the file branch of `source::load` delegate to a file-only loader. In `AnalysisService::response_source`, match file vs database once. Pass the file locator through `response_file`, registration, `start`, the blocking task and `execute_analysis`. Have `AnalysisExecutor` and its injected test closures accept a file locator rather than a bare `PathBuf`. The executor must load that locator directly, not select a parser from a cache key.
- Keep the catalogue locator’s path for loading, post-read stat and parse-error classification. Fingerprint sidecars beside the canonical path for the key; loaders read them beside the path they receive. These paths coincide in production discovery but need not coincide in tests. Keep fingerprinting off the async executor, register flights before permit acquisition, and leave locks, permit limits, error fan-out, cancellation and cache eviction unchanged. Change the Pi-only `#[cfg(test)]` helpers `AnalysisService::response` and `analysis_cache_key` to take an explicit file locator, or name them `response_pi` and `pi_analysis_cache_key` if their callers are exclusively Pi tests. Run the existing gate-based executor tests before proceeding.

## 3. Express file and database cache identities separately

- Replace the flat fields of `AnalysisCacheKey` in `src/server/analysis.rs` with alternatives for a file analysis and an OpenCode snapshot. Both include response options: tokenisation policy, analysis schema version, output version and compact-preview flag. Performance diagnostics remain excluded. Prefer a file-specific key type that the file executor can take directly; wrap it in the common key for cache/flight lookup. Pass locator and file key together from the same preflight operation, not from independent caller-supplied inputs.
- File key: canonical path, reader (including Claude main/subagent), byte length, modification time in nanoseconds, and the existing auxiliary fingerprint when applicable. Use a typed optional auxiliary fingerprint for VS Code traces or Copilot workspace metadata. Today both are stored in `database_revision` and hashed under an OpenCode tag with a string label; neither represents an OpenCode snapshot. Preserve the current recheck semantics: main-file size and mtime are checked on success and after a load failure; auxiliary fingerprints are computed at preflight. Strengthening race detection is not part of this refactor.
- Database key: database path, native session ID and revision bytes from the committed snapshot. No reader or dummy file fields. Retain `DatabaseFlightKey`: requests can join before the revision is known. Inside the worker, read the committed snapshot **before** consulting the response cache or returning 304; analyse that same snapshot on a miss. Do not use the catalogue's source revision, database mtime or WAL notifications as substitutes.
- Change `etag_for_key` to explicitly encode the variant and every field affecting equality, including options and auxiliary inputs. Use distinct tags and unambiguous string/path boundaries; length-prefix the path’s `OsStr::as_encoded_bytes()` rather than hashing replacement characters. This is a local opaque validator, not a portable on-disk encoding. For Pi deduplication use `PathBuf` equality directly. Keep BLAKE3 and the quoted HTTP form. Test equality and separation, not exact historical strings. The list ETag is a separate generation/revision token and must not change as a result of this encoding change. No analysis schema or output version bump just to invalidate old ETags.

## 4. Verification and completion

1. Before compiling the baseline, build `web/dist` with `scripts/build-web.sh` if absent. Run `cargo test --locked server::` and `cargo test --locked report::` before editing and after each independently compiling step. After step 2 run `cargo test --all-targets --locked`: analysis contract, unrecorded usage, usage export, OpenCode replay, source and session-totals tests also construct locators.
2. Adapt existing key tests to construct realistic typed keys. Use a small table for distinctions not already covered: same file with different reader or Claude subtype; same database with different native IDs/revisions; same analysis with different preview modes, tokenisation or versions; same inputs with diagnostics toggled. Check both key equality and ETags. Keep the existing workspace and trace change tests and OpenCode HTTP/WAL tests. For an unchanged result and matching ETag expect 304; after a relevant change expect 200 and a different ETag. A missing or unreadable source must not produce a stale 304.
3. Retain the existing source-changed, concurrent request, initiator cancellation, panic, retry, oversized response and eviction tests. Check CLI report/show and item-content behaviour as well as analysis JSON: these consumers also depend on locators. Do not update parity digests merely to make tests pass; analysis outputs are not meant to change.
4. Run `cargo fmt --check`, `cargo clippy --all-targets --locked -- -D warnings` and `cargo test --all-targets --locked`, then the project's `scripts/check.sh` in its documented environment. Update the loading/cache paragraph in `docs/architecture.md`, check the fingerprint descriptions in `docs/sources/vscode-copilot.md` and `docs/sources/claude-code.md`, and replace the comment in `src/server/analysis.rs` promising unchanged literal ETags. Review the diff for accidental schema/JSON changes, altered session references, new path parsing, or a test-only escape route that can create an entry without a locator.

The steps are review boundaries, not a request to commit. No changes to scanner retry policy, cross-reader ancestry, frontend validation, BB protocol, cache capacity or public endpoints are included.

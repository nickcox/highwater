# TokenPlume data semantics

What TokenPlume reads, what it calculates locally, what it takes from recorded provider usage, and how missing values are kept distinct. For using the interface, see the [user guide](user-guide.md).

## Tokenization

Tokenization is local and offline. `auto` uses the pinned `o200k_base`/`cl100k_base` tokenizers for recognized OpenAI model families, provider serialization estimates where documented, and a versioned Unicode-character heuristic for unknown models. GPT-6-family models on OpenAI/OpenAI Codex (and GitHub Copilot's OpenAI Responses route) provisionally use `o200k_base`: local text-only output counts support this choice, but OpenAI has not published a GPT-6 encoding mapping. Calculated item counts remain estimates, not exact billed prompt tokens. Use `--tokenization strict` to report unsupported profiles without fallback, `heuristic` to force the fallback, or `off` to disable token analysis. Add `--perf-diagnostics` to emit aggregate stage timings and operation counts without session content.

## OpenCode support

Without explicit source flags, discovery includes an existing `~/.pi/agent/sessions` and existing `opencode.db` / `opencode-stable.db` files under `$XDG_DATA_HOME/opencode` (default `~/.local/share/opencode`). Either harness can be absent. An explicit `--session-root` remains Pi-only unless `--opencode-db` is also provided; explicit database paths replace the default database list. Missing explicitly configured sources fail startup. Sources are read locally, never migrated or opened with a writable fallback; no credentials or account tables are queried, and referenced files/URLs are never fetched.

| Area | Current support |
| --- | --- |
| Storage | Legacy `session` / `message` / `part` and modern `session_v2` / `session_message`, including modern-only databases. Modern records use native `seq` order. Mixed databases select one generation per session, never a combined usage ledger. Experimental context/input layouts remain unsupported. |
| Replay | Legacy invocation/results and pruning revisions; modern inline reasoning/tools, usage-only assistants, recorded system updates and injected context. Modern completed compactions replace history with the recorded summary **and serialized recent context**. Failed/running compactions do not reset history; terminal and superseded checkpoints have no invented exposure. Reverts, native encrypted checkpoints, unknown record types, and unaudited legacy tail/synthetic/multi-step histories fail closed. |
| Coverage | A visible **Reconstructed conversation only** notice and structured limitations. Frozen modern system updates are retained, but are not a complete historical baseline. Generation selection, migrated request boundaries, missing compaction usage, and multi-request compaction billing aggregates are explicitly qualified. |
| Usage / cost | Independent optional recorded counters and harness-recorded total cost. Whether output includes reasoning is decided per step from the stored `total`, which OpenCode takes from the provider and which counts reasoning once: up to v1.3.x output included reasoning (total = input + output + cache), and from v1.4.0 it is stored separately (total = input + output + reasoning + cache). Modern records have no `total`, so a modern record uses the legacy step-finish copy with the same message ID when one exists and all its counters match. Layout and creation version are never used for this. A step whose total fits neither, or that has none, keeps output unavailable. The recorded cost is kept as recorded; the [cost assessment](#cost-assessment) adds estimates and API-equivalent costs separately. No Pi cost allocation, cache economics, duration, or billed-charge claim. |
| Freshness | Committed SQLite snapshots and per-session content digests before cache hits/304s; DB/WAL/SHM hints plus two-second polling for catalogue invalidation and database replacement. Healthy sources advance while failed sources retain their last-good catalogue. |

For duplicate IDs within one database, a strictly newer legacy session row selects legacy; otherwise a modern projection wins. A missing modern projection falls back to legacy only when timestamps tie and legacy messages exist. A newer empty modern history never resurrects older legacy content. This recency rule is a qualified selection policy, not proof of writer authority. IDs duplicated across different databases remain ambiguous.

SQLite read budgets are 32 MiB per value/row, 256 MiB aggregate loaded strings, 200,000 legacy message-plus-part or modern message rows, and 50,000 discovered sessions; the busy timeout is 250 ms. These are source-read budgets, not total RSS limits. Mixed large-source/oversized-response stress measured roughly 848 MiB sampled server RSS; heavy sessions need substantial memory. Conditional requests still read/hash a current snapshot (about 445 ms for the synthetic ~128 MiB source). Responses above the 16 MiB response-cache budget are regenerated even for conditional requests. A response represents the committed snapshot read by that request; later commits appear on refresh. See [implementation evidence and remaining audits](../plans/archive/opencode-analysis-notes.md).

## Analysis API

The primary endpoint is `GET /api/sessions/{id}/analysis`, where `id` is the portable `pi-…` / `opencode-…` reference returned by `GET /api/sessions`. Legacy Pi canonical-path lookup remains constrained to discovered files; OpenCode database paths/native IDs are not accepted from HTTP. It contains labels, structural metadata, bounded reader-facing content previews, and normalized economics, but it does not duplicate full raw JSONL records or provider payloads. `ContextItem.label` is a bounded source-aware title/accessibility label; Pi tool results use their matching selected-branch invocation when available: **Assistant · write** labels the request, while **Write result · filename** labels the returned result (likewise Read, Edit, Bash, Grep and Find). Previews remain separate content and are never reinterpreted as arguments. Top-level `schemaVersion` is the sole public envelope-version marker; the current response schema is version 13. Each model call lists its context items as positions in `contextItems` (`contextItemIndexes`, `addedItemIndexes`, `droppedItemIndexes`), in context order, rather than repeating item IDs; `indexAnalysis` resolves them back to IDs. Failed/aborted Pi attempts with explicit default-zero counters expose those values in `usage.placeholder`, not as measured usage or cost. Qualified counters are unavailable, per-call cumulative totals retain missingness, and the reported-input reference breaks at these attempts. Session totals (`reportedPromptTokens`, `reportedCompletionTokens`, `reportedReasoningTokens`, `reportedCostTotal`) are subtotals over the calls that recorded a value; `reportedUsageCoverage` and `reportedCostCoverage` count recorded calls, failed attempts and other missing calls, and the summary shows that coverage whenever it is incomplete. Shared call inspectors show **Recorded output** (`usage.recordedOutput`) and **Recorded reasoning** (`usage.reasoning`, when present) as separate source counters. `usage.outputReasoningRelationship` describes their overlap; accounting details stay in the usage disclosure, not a headline warning. The existing `usage.output` / `reportedCompletionTokens` remain normalized completion totals (including reasoning exactly once when known), and are not replaced by raw counters for costs, cumulative totals, or throughput. Missing counters are not inferred from reasoning text or treated as zero. OpenCode responses include `reconstruction: {status: "partial", explanationCodes: [...]}`; Pi omits this optional field. Responses include an ETag and support `If-None-Match` with an empty-body `304 Not Modified` response.

Each `modelCalls[].timing` preserves `startedAtMs` (Pi assistant-message initialization) and `recordedAtMs` (session-entry persistence) as nullable UTC epoch milliseconds. Valid instants are retained independently, even for unknown/custom APIs. For checked Pi built-in APIs, a positive same-response interval yields `durationMs` with basis `pi-message-timestamps`; this is approximate client-observed elapsed time, including waiting, retries and possible extension processing—not generation-only time or subsequent tool execution. Successful terminal responses with reported output yield `effectiveOutputTokensPerSecond = output × 1000 / durationMs`; output already includes reasoning, which is not added twice. Failed/aborted response rates, missing output, absent/reversed/zero intervals, and unverified API timing semantics remain unavailable. Malformed optional timestamps become null without discarding otherwise usable sessions. No inter-message gaps, TTFT or live-stream timing are inferred. The Model call panel exposes qualified elapsed time and effective output rate; absolute instants are captured for future use, not displayed yet.

Raw public analysis integers are limited to `Number.MAX_SAFE_INTEGER`; invalid required/count source/normalized values are rejected before successful serialization. Derived range exhaustion remains qualified `null`, never a recovered total or misleading subtotal. Exposure coverage distinguishes an observed numeric zero, partial available observations, and unavailable values; terminal summaries are structural/selectable but have no fabricated exposure. Known request framing is a text-only approximation for supported chat routes, not universal provider serialization or billing.

Internal output/cache identity is **25**, tokenization profile identity is **v4** (opaque, delimiter-safe IDs preserving absent versus literal target values), and payload fingerprint encoding is **4**. These are not additional public envelope-version fields. A Pi session's final line is skipped while it is still being written (no trailing newline and not yet valid JSON); every completed line must be valid. Pi source verification retains size/mtime identity: rewrites preserving both can escape detection, and filesystem races are not completely eliminated. OpenCode cache identity uses the configured database, native session ID, and content digest from a committed read transaction instead of file mtime/size. Shutdown drain timeouts acknowledge that blocking work may remain; detached scan results cannot publish after shutdown.

## Pi system context

Recorded Pi system instructions and tool declarations are replayed into immutable per-call context revisions, including ordered section patches, tool changes and compaction checkpoints. They appear in River and Composition without being charged twice or included as summary-source lineage. Cumulative Composition accounts for each revision's actual item-call appearances; it does not add old and new revisions to the same call. Older logs can lack this material: absence is not evidence of zero tokens. Provider-reported usage and cost remain independent of these local estimates.

System/tool estimates describe logical replayed context, not exact provider wire framing; generic declaration JSON and provider-specific mid-conversation updates can differ from the transmitted request. These estimates therefore report partial coverage. Pi 1.0.4's docs describe `replace: true`, but its installed replay helpers ignore it; TokenPlume marks affected histories unavailable rather than guessing a reset, until a complete compaction checkpoint restores a known baseline. An authoritative recorded modern loadout supersedes legacy standalone declaration records. No historical prompt is inferred from current installation files or provider residuals.

## Cost assessment

Each model call has a `costAssessment`, and the session has a `costSummary` that keeps billed cost and API-equivalent cost apart. The design and its reasons are in the [implementation plan](../plans/archive/cost-estimates-implementation-plan.md).

| Billing | Situation | Kind | Amount |
| --- | --- | --- | --- |
| Per token | The harness recorded a cost above $0 | `recorded` | The recorded cost |
| Per token | The recorded cost is $0 or missing, and the provider listed the model at $0 then | `free` | $0 |
| Per token | The recorded cost is $0 or missing, and the provider listed a price then | `estimated` | Token counts × the provider's rate on that date |
| Subscription | Any | `apiEquivalent` | Token counts × the lab's API rate on that date; not a charge |
| Any | No price, time or token counts, or a failed attempt | `unknown` | None |

- **Billing mode** comes from `data/prices/billing-modes.toml`: Pi's `openai-codex` provider is a ChatGPT-plan subscription, and GitHub Copilot was a subscription (charged per request) before 1 June 2026 and per token from then. OpenCode records a ChatGPT-plan login under the plain `openai` provider, so an OpenCode `openai` call recorded at $0, while models.dev lists a price for that model at that time, is treated as a subscription. The call details state this inference.
- **Prices** come from `data/prices/prices.json`, generated from models.dev's git history plus amendments, including corrections converted from wakamex/model-prices; see [data/prices/README.md](../data/prices/README.md). Each rate records when it started and whether that date is documented, first observed on a pricing page, or a models.dev commit date, which can lag the provider's change by days. A call before a model's first listed price uses that first price. TokenPlume never downloads prices.
- **The calculation** is uncached input, cache reads, cache writes and output, each times its rate, using the long-prompt tier that applies. A missing cache rate falls back to the input rate, and one-hour cache writes cost twice the input rate. Output must include reasoning exactly once. When that cannot be established for a call (see the OpenCode usage row above), the amount is a range from output alone to output plus reasoning, shown when the ends differ by at least 1 %.
- **Pi's own figure** for subscription calls is kept in `recordedByHarness` but not used as the amount, so Pi and OpenCode calls are priced the same way. Pi recorded its figure at call time with its own rates, which can differ, for example for GPT-5.6 Sol calls after OpenAI's 21 August 2026 price cut.
- `reportedCostTotal` and `reportedCostCoverage` keep their meaning: the harness's recorded costs, unchanged.

## Cache and cost policies

GitHub Copilot's `openai-responses` route has a dedicated three-bucket cache policy: prompt tokens are normalized uncached input + cache read + cache write. Missing buckets remain incomplete, not zero; complete zero prompts have no ratios. Pi's configured-rate cost components can be interpreted when all are recorded, but are **not Copilot subscription charges, premium-request counts or invoices**. Direct OpenAI policies remain conservative about older adapter-dropped writes and reject unexpected positive write buckets; model names alone never grant policy support.

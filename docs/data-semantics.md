# TokenPlume data semantics

What TokenPlume reads, what it calculates locally, what it takes from recorded provider usage, and how missing values are kept distinct. For using the interface, see the [user guide](user-guide.md).

## Tokenization

Tokenization is local and offline. `auto` uses the pinned `o200k_base`/`cl100k_base` tokenizers for recognized OpenAI model families, provider serialization estimates where documented, and a versioned Unicode-character heuristic for unknown models. GPT-6-family models on OpenAI/OpenAI Codex (and GitHub Copilot's OpenAI Responses route) provisionally use `o200k_base`: local text-only output counts support this choice, but OpenAI has not published a GPT-6 encoding mapping. Calculated item counts remain estimates, not exact billed prompt tokens. Use `--tokenization strict` to report unsupported profiles without fallback, `heuristic` to force the fallback, or `off` to disable token analysis. Add `--perf-diagnostics` to emit aggregate stage timings and operation counts without session content.

### Claude models

Anthropic publishes no tokenizer for Claude 3 or later. TokenPlume counts Claude models with a Rust port of [ctok](https://github.com/sanderland/ctok) (MIT, commit `8c43ffd`), which reconstructs each tokenizer generation from `count_tokens` measurements. The vocabularies are in `data/tokenization/`, converted by `scripts/convert-ctok-vocabulary.py`.

| Topic | Rule |
| --- | --- |
| Matching | A model is matched by its ID whichever provider served it (Anthropic, GitHub Copilot, Bedrock, Vertex and others), after removing route prefixes and suffixes such as `anthropic/`, `us.anthropic.`, `@…`, `-v1:0` and a trailing date. Claude 3 to Opus 4.6 use `ctok-claude-v3`; Opus 4.7 uses `ctok-claude-v4.7`; Opus 4.8 and later, and the Sonnet 5 and Fable models, use `ctok-claude-v4.8`. A Claude model that is not in these rules (for example a new Haiku) uses `ctok-claude-v4.8` with the rule `assumed-latest-claude-ctok`, and the interface says the model has not been measured. Models before Claude 3 keep the character estimate. The method is `apiSerializationEstimate`. |
| Counts | Each item is counted as the content of one message. The fixed tokens Anthropic adds per message (7, 11 or 6 by generation) are not added, because TokenPlume does not know how items are grouped into messages. `scripts/check-claude-tokenizer-parity.py` checks that the port counts exactly as Python ctok does on ctok's fixtures and, optionally, the local Claude Code texts. |
| Tool calls | A tool call is counted in the form Claude models read: `<invoke name="…">`, one `<parameter name="…">value</parameter>` line per argument with string values unescaped, and `</invoke>`. Arguments that are not a JSON object are counted as recorded. Counting the arguments' JSON text instead overestimates them by about 15%, because of the escaping. |
| Thinking | Anthropic keeps a response's thinking in later requests and bills it as input, although a transcript records it only as a summary or not at all. When a response reports its reasoning tokens (Claude Code's `usage.output_tokens_details.thinking_tokens`; Pi's reasoning count on Claude models), the thinking is a separate context item of kind `thinking`, sized by that count (method `reportedUsage`), and the recorded thinking text is no longer counted in the response item. OpenCode records no reasoning count for its Claude messages, so it has no thinking items. Opus 4.5 and later, Sonnet 4.6 and later, Haiku 5.5 and later, and the Fable and Mythos models keep thinking from all earlier turns; earlier models keep it until the next user message. For a call to another model the item counts 0 tokens, with the note `thinkingNotReadByModel`, because a model does not read another model's thinking. |
| Accuracy | `scripts/measure-claude-usage.py` fits the growth in each call's reported prompt size against the estimates of the items it adds. On the local sessions when this was written, Pi's Claude sessions match exactly (each kind of item at 1.00, a median error of 0.5% per step, nothing left over per tool round trip). Claude Code's match at 0.91–0.98 per kind and leave about 140 tokens per tool round trip, most likely content Claude Code adds to requests without recording it. The system prompt and tool definitions are not recorded at all, so a Claude Code call's reported input is always larger than its calculated context. |

## OpenCode support

Without explicit source flags, discovery includes an existing `~/.pi/agent/sessions` and existing `opencode.db` / `opencode-stable.db` files under `$XDG_DATA_HOME/opencode` (default `~/.local/share/opencode`). Either harness can be absent. An explicit `--session-root` remains Pi-only unless `--opencode-db` is also provided; explicit database paths replace the default database list. Missing explicitly configured sources fail startup. Sources are read locally, never migrated or opened with a writable fallback; no credentials or account tables are queried, and referenced files/URLs are never fetched.

| Area | Current support |
| --- | --- |
| Storage | Legacy `session` / `message` / `part` and modern `session_v2` / `session_message`, including modern-only databases. Modern records use native `seq` order. Mixed databases select one generation per session, never a combined usage ledger. Experimental context/input layouts remain unsupported. |
| Replay | Legacy invocation/results and pruning revisions; modern inline reasoning/tools, usage-only assistants, recorded system updates and injected context. Modern completed compactions replace history with the recorded summary **and serialized recent context**. Failed/running compactions do not reset history; terminal and superseded checkpoints have no invented exposure. Reverts, native encrypted checkpoints, unknown record types, and unaudited legacy tail/synthetic/multi-step histories fail closed. |
| Coverage | A visible **Reconstructed conversation only** notice and structured limitations. Frozen modern system updates are retained, but are not a complete historical baseline. Generation selection, migrated request boundaries, missing compaction usage, and multi-request compaction billing aggregates are explicitly qualified. |
| Usage / cost | Independent optional recorded counters and harness-recorded total cost. Whether output includes reasoning is decided per step from the stored `total`, which OpenCode takes from the provider and which counts reasoning once: up to v1.3.x output included reasoning (total = input + output + cache), and from v1.4.0 it is stored separately (total = input + output + reasoning + cache). Modern records have no `total`, so a modern record uses the legacy step-finish copy with the same message ID when one exists and all its counters match. Layout and creation version are never used for this. A step whose total fits neither, or that has none, keeps output unavailable. The recorded cost is kept as recorded; the [cost assessment](#cost-assessment) adds estimates and API-equivalent costs separately. No Pi cost allocation, cache economics, duration, or billed-charge claim. |
| Freshness | Committed SQLite snapshots and per-session content digests before cache hits/304s; DB/WAL/SHM hints plus two-second polling for catalogue invalidation and database replacement. Healthy sources advance while failed sources retain their last-good catalogue. |

For duplicate IDs within one database, a strictly newer legacy session row selects legacy; otherwise a modern projection wins. A missing modern projection falls back to legacy only when timestamps tie and legacy messages exist. A newer empty modern history never resurrects older legacy content. This recency rule is a qualified selection policy, not proof of writer authority. IDs duplicated across different databases remain ambiguous.

SQLite read budgets are 32 MiB per value/row, 256 MiB aggregate loaded strings, 200,000 legacy message-plus-part or modern message rows, and 50,000 discovered sessions; the busy timeout is 250 ms. These are source-read budgets, not total RSS limits. Mixed large-source/oversized-response stress measured roughly 848 MiB sampled server RSS; heavy sessions need substantial memory. Conditional requests still read/hash a current snapshot (about 445 ms for the synthetic ~128 MiB source). Responses above the 16 MiB response-cache budget are regenerated even for conditional requests. A response represents the committed snapshot read by that request; later commits appear on refresh. See [implementation evidence and remaining audits](../plans/archive/opencode-analysis-notes.md).

## Claude Code support

Without explicit source flags, discovery also includes `$CLAUDE_CONFIG_DIR/projects` (default `~/.claude/projects`) when it exists. `--claude-root` (repeatable) replaces that default; an explicit `--session-root` alone turns it off, as it does for OpenCode. Transcripts are read locally and never written; `~/.claude.json`, credentials and referenced files are never read. The design and the evidence for each rule are in the [implementation plan](../plans/archive/claude-code-implementation-plan.md) and [analysis notes](../plans/archive/claude-code-analysis-notes.md). Claude Code is not open source, so the rules come from transcripts written by versions 2.1.229 and 2.1.287 and from synthetic fixtures; other versions may record things differently.

| Area | Current support |
| --- | --- |
| Discovery | Main sessions are `.jsonl` files directly inside a project directory; subagents are `<session>/subagents/agent-*.jsonl`, listed as child sessions of their parent with the type from their `.meta.json`. Titles are the latest custom title, otherwise the latest generated title. The working directory comes from the records' `cwd`, not the project directory's name. References are `claude-code-…`, derived from the session ID (plus the agent ID for a subagent). |
| Branch | The active branch ends at the last-written user or assistant record with no user or assistant children; `system` records such as away summaries are never the end. A rewind leaves the abandoned branch out. A compaction boundary continues the walk from its `logicalParentUuid`. Parallel tool results that Claude Code writes as children of an earlier record of the same response are attached after that response. |
| Calls and context | One call per API response (`message.id`), however many records it was written as, with usage from its last record. User messages (including slash commands and their output), `isMeta` user records, assistant responses, tool results, and attachments with rendered text are context items. API error records are failed attempts with placeholder usage, and their error text is not context. |
| Compaction | The summary starts the new context, followed by the records in `preservedSegment`, which continue as retained items, and then the records after the summary. A boundary without `preservedSegment` keeps only the summary and is qualified. |
| Coverage | Always partial: the system prompt, tool definitions and Claude Code's own model calls (titles, summaries, compaction) are not recorded. Missing compaction usage, unverified retention, attachments recorded without their text (2.1.229) and unsupported content such as `tool_reference` blocks are reported when they occur. |
| Usage | `input_tokens` is uncached input; cache reads, cache writes and the one-hour part of cache writes are kept separately. Output includes thinking, which is also kept as reasoning. Duration and output rate are unavailable, because no request start time is recorded. |
| Cost | No cost is recorded per call. See [cost assessment](#cost-assessment) for how calls are priced. When the transcript has a `cost-state` record, `session.harnessSessionCost` gives Claude Code's own running total since its start time; it includes subagents and Claude Code's own calls, so it is shown only in Session details and never added to other costs. |
| Freshness | The same size and modification-time fingerprint as Pi files; an unfinished last line is skipped. The catalogue reads each transcript's listing fields again only when its size or modification time changes. |

A synthetic 16.8 MB transcript (701 calls, 2,798 context items, one compaction) took about 0.5 s for a cold release-build analysis, 4 ms for a cached one and under 1 ms for a `304`, with about 126 MiB peak sampled server memory (`python3 scripts/benchmark-claude-code.py`).

## Analysis API

The primary endpoint is `GET /api/sessions/{id}/analysis`, where `id` is the portable `pi-…` / `opencode-…` / `claude-code-…` reference returned by `GET /api/sessions`. Legacy Pi canonical-path lookup remains constrained to discovered files; OpenCode database paths/native IDs are not accepted from HTTP. It contains labels, structural metadata, bounded reader-facing content previews, and normalized economics, but it does not duplicate full raw JSONL records or provider payloads. `ContextItem.label` is a bounded source-aware title/accessibility label; Pi tool results use their matching selected-branch invocation when available: **Assistant · write** labels the request, while **Write result · filename** labels the returned result (likewise Read, Edit, Bash, Grep and Find). Previews remain separate content and are never reinterpreted as arguments. Top-level `schemaVersion` is the sole public envelope-version marker; the current response schema is version 15. Each model call lists its context items as positions in `contextItems` (`contextItemIndexes`, `addedItemIndexes`, `droppedItemIndexes`), in context order, rather than repeating item IDs; `indexAnalysis` resolves them back to IDs. Failed/aborted Pi attempts with explicit default-zero counters expose those values in `usage.placeholder`, not as measured usage or cost. Qualified counters are unavailable, per-call cumulative totals retain missingness, and the reported-input reference breaks at these attempts. Session totals (`reportedPromptTokens`, `reportedCompletionTokens`, `reportedReasoningTokens`, `reportedCostTotal`) are subtotals over the calls that recorded a value; `reportedUsageCoverage` and `reportedCostCoverage` count recorded calls, failed attempts and other missing calls, and the summary shows that coverage whenever it is incomplete. Shared call inspectors show **Recorded output** (`usage.recordedOutput`) and **Recorded reasoning** (`usage.reasoning`, when present) as separate source counters. `usage.outputReasoningRelationship` describes their overlap; accounting details stay in the usage disclosure, not a headline warning. The existing `usage.output` / `reportedCompletionTokens` remain normalized completion totals (including reasoning exactly once when known), and are not replaced by raw counters for costs, cumulative totals, or throughput. Missing counters are not inferred from reasoning text or treated as zero. OpenCode and Claude Code responses include `reconstruction: {status: "partial", explanationCodes: [...]}`; Pi omits this optional field. `session.harnessSessionCost` is `{totalUsd, sinceMs}` for a Claude Code session whose transcript records its own total, otherwise `null`. Responses include an ETag and support `If-None-Match` with an empty-body `304 Not Modified` response.

Each `modelCalls[].timing` preserves `startedAtMs` (Pi assistant-message initialization) and `recordedAtMs` (session-entry persistence) as nullable UTC epoch milliseconds. Valid instants are retained independently, even for unknown/custom APIs. For checked Pi built-in APIs, a positive same-response interval yields `durationMs` with basis `pi-message-timestamps`; this is approximate client-observed elapsed time, including waiting, retries and possible extension processing—not generation-only time or subsequent tool execution. Successful terminal responses with reported output yield `effectiveOutputTokensPerSecond = output × 1000 / durationMs`; output already includes reasoning, which is not added twice. Failed/aborted response rates, missing output, absent/reversed/zero intervals, and unverified API timing semantics remain unavailable. Malformed optional timestamps become null without discarding otherwise usable sessions. No inter-message gaps, TTFT or live-stream timing are inferred. The Model call panel exposes qualified elapsed time and effective output rate; absolute instants are captured for future use, not displayed yet.

Raw public analysis integers are limited to `Number.MAX_SAFE_INTEGER`; invalid required/count source/normalized values are rejected before successful serialization. Derived range exhaustion remains qualified `null`, never a recovered total or misleading subtotal. Exposure coverage distinguishes an observed numeric zero, partial available observations, and unavailable values; terminal summaries are structural/selectable but have no fabricated exposure. Known request framing is a text-only approximation for supported chat routes, not universal provider serialization or billing.

Internal output/cache identity is **30**, tokenization profile identity is **v4** (opaque, delimiter-safe IDs preserving absent versus literal target values), and payload fingerprint encoding is **4**. These are not additional public envelope-version fields. A Pi session's final line is skipped while it is still being written (no trailing newline and not yet valid JSON); every completed line must be valid. Pi source verification retains size/mtime identity: rewrites preserving both can escape detection, and filesystem races are not completely eliminated. OpenCode cache identity uses the configured database, native session ID, and content digest from a committed read transaction instead of file mtime/size. Claude Code transcripts use the Pi file identity plus the file kind and the `--claude-billing` setting, so a response cached under one setting is never returned under the other. Shutdown drain timeouts acknowledge that blocking work may remain; detached scan results cannot publish after shutdown.

## Pi system context

Recorded Pi system instructions and tool declarations are replayed into immutable per-call context revisions, including ordered section patches, tool changes and compaction checkpoints. They appear in River and Composition without being charged twice or included as summary-source lineage. Cumulative Composition accounts for each revision's actual item-call appearances; it does not add old and new revisions to the same call. Older logs can lack this material: absence is not evidence of zero tokens. Provider-reported usage and cost remain independent of these local estimates.

System/tool estimates describe logical replayed context, not exact provider wire framing; generic declaration JSON and provider-specific mid-conversation updates can differ from the transmitted request. These estimates therefore report partial coverage. Pi 1.0.4's docs describe `replace: true`, but its installed replay helpers ignore it; TokenPlume marks affected histories unavailable rather than guessing a reset, until a complete compaction checkpoint restores a known baseline. An authoritative recorded modern loadout supersedes legacy standalone declaration records. No historical prompt is inferred from current installation files or provider residuals.

## Cost assessment

Each model call has a `costAssessment`, and the session has a `costSummary` that keeps billed cost and API-equivalent cost apart. The design and its reasons are in the [implementation plan](../plans/archive/cost-estimates-implementation-plan.md).

| Billing | Situation | Kind | Amount |
| --- | --- | --- | --- |
| Per token | The harness recorded a cost above $0 | `recorded` | The recorded cost |
| Per token | The recorded cost is $0 or missing, and the provider listed the model at $0 then | `free` | $0 |
| Per token | The recorded cost is $0 or missing, and the provider listed a price then | `estimated` | Token counts × the provider's rate on that date |
| Subscription | Any | `apiEquivalent` | Token counts × the lab's API rate on that date; not a charge |
| Any | No price, time or token counts, or a failed attempt | `unknown` | None |

- **Billing mode** comes from `data/prices/billing-modes.toml`: Pi's `openai-codex` provider is a ChatGPT-plan subscription, and GitHub Copilot was a subscription (charged per request) before 1 June 2026 and per token from then. OpenCode records a ChatGPT-plan login under the plain `openai` provider, so an OpenCode `openai` call recorded at $0, while models.dev lists a price for that model at that time, is treated as a subscription. The call details state this inference. Claude Code transcripts do not record whether a session used a subscription or an API key. Claude Code's `anthropic` calls are a subscription by default, so they are API-equivalent; Anthropic's API rate is also what an API key pays, so the amount is the same either way. `--claude-billing api` treats them as billed per token instead (`estimated`, classification rule `claudeCodeBillingSetting`).
- **Prices** come from `data/prices/prices.json`, generated from models.dev's git history plus amendments, including corrections converted from wakamex/model-prices; see [data/prices/README.md](../data/prices/README.md). Each rate records when it started and whether that date is documented, first observed on a pricing page, or a models.dev commit date, which can lag the provider's change by days. A call before a model's first listed price uses that first price. TokenPlume never downloads prices.
- **The calculation** is uncached input, cache reads, cache writes and output, each times its rate, using the long-prompt tier that applies. A missing cache rate falls back to the input rate, and one-hour cache writes cost twice the input rate. Output must include reasoning exactly once. When that cannot be established for a call (see the OpenCode usage row above), the amount is a range from output alone to output plus reasoning, shown when the ends differ by at least 1 %.
- **Pi's own figure** for subscription calls is kept in `recordedByHarness` but not used as the amount, so Pi and OpenCode calls are priced the same way. Pi recorded its figure at call time with its own rates, which can differ, for example for GPT-5.6 Sol calls after OpenAI's 21 August 2026 price cut.
- `reportedCostTotal` and `reportedCostCoverage` keep their meaning: the harness's recorded costs, unchanged.

## Cache and cost policies

Claude Code calls use the `anthropic-messages-cache-v1` policy for cache figures (prompt tokens are uncached input + cache read + cache write). Pi's recorded cost-component rules do not apply to them, because Claude Code records no cost.

GitHub Copilot's `openai-responses` route has a dedicated three-bucket cache policy: prompt tokens are normalized uncached input + cache read + cache write. Missing buckets remain incomplete, not zero; complete zero prompts have no ratios. Pi's configured-rate cost components can be interpreted when all are recorded, but are **not Copilot subscription charges, premium-request counts or invoices**. Direct OpenAI policies remain conservative about older adapter-dropped writes and reject unexpected positive write buckets; model names alone never grant policy support.
